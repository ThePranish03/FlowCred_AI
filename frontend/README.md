# FlowCred AI - Explainable Accounts Receivable Intelligence

A production-structured React frontend for invoice risk, payment-delay prediction and customer segmentation. The app is built around a swappable API layer: it runs today against recorded model artifacts and is ready to point at the FastAPI backend without changing page components.

## Stack

- React 18, TypeScript, Vite 6
- Tailwind CSS 3 with hand-authored shadcn-style Radix primitives
- React Router 6, TanStack Query 5, Axios
- Zustand with persistence for the demo session and preferences
- Recharts for charts, Papaparse for CSV validation
- jsPDF + jspdf-autotable for PDF export, native Blob download for CSV

## Quick start

```bash
cd frontend
npm install
npm run dev
```

The dev server prints a local URL (for example `http://localhost:5173`). Sign in with any valid email and a password of at least six characters, choosing one of the four demo roles.

```bash
npm run build     # tsc --noEmit && vite build
npm run preview   # serve the production bundle
```

Node 18 or newer is required.

## Demo mode and live mode

The API mode is selected at build time:

```bash
# .env.local
VITE_API_MODE=demo          # default
VITE_API_BASE_URL=/api/v1
```

- `demo` - reads JSON fixtures from `public/demo-data` through `src/api/demo.ts`. Filtering, pagination, search and report assembly happen in the browser.
- `live` - sends requests through `src/api/client.ts` to `VITE_API_BASE_URL`.

Swap points:

| Concern | File |
| --- | --- |
| Endpoint selection | `src/api/index.ts` |
| Demo adapter | `src/api/demo.ts` |
| Live Axios client | `src/api/client.ts` |
| Response contracts | `src/types/index.ts` |
| Query hooks | `src/api/queries.ts` |

Rebuild after changing environment variables. No page component imports the demo adapter directly.

## Demo data provenance

`public/demo-data` is generated by `scripts/generate-demo-data.py` from the project's recorded artifacts:

- `data/processed/*.csv`
- `reports/**/*.csv` and `*.json`
- `models/*_metadata.json`
- the saved classifier, read only for its recorded `feature_importances_`

No prediction, financial value or metric is invented. Invoices without a model output keep `null` scores.

Regenerate from the repository root:

```bash
cd frontend
python scripts/generate-demo-data.py
```

The generator requires Python with pandas, numpy, scikit-learn and joblib-compatible loading for the saved artifacts. The output is normalized to strict JSON; NaN and infinity values are written as `null`.

Current snapshot:

- 48,833 cleaned invoices, 1,424 customers, 2018-12-30 to 2020-05-22
- 5,873 scored test-window invoices; the scored window contains paid invoices only
- mixed USD and CAD with no FX conversion
- K-Means with K=6 (silhouette 0.8006, mean seed ARI 0.9742)

## Data integrity rules enforced by the UI

- The three supplied models are never retrained, replaced or tuned by the frontend.
- Model files are never loaded in the browser; inference must run on the backend.
- No predictions, customer records, metrics or forecasts are fabricated.
- Invoices without a recorded score display "Not scored" instead of an estimate.
- The scored window contains paid invoices, so open high-risk exposure is shown as $0 with an explanation.
- Global feature importance is labelled as global; per-invoice SHAP is shown only if the backend supplies it.
- Mixed-currency aggregates are labelled nominal; no FX conversion is implied.
- K=6 is disclosed as a modelling choice; silhouette peaks at K=2 in the recorded comparison.
- `/cash-flow-forecast` shows a historical weekly forecast per currency, labelled with its as-of date, invoice-clearance proxy limitation and derived-daily-estimate status.
- Model metrics are labelled as recorded historical evaluation, not guarantees.

## CSV validation

Data Management validates a CSV entirely in the browser before any upload:

- required columns: `invoice_id`, `customer_id`, `name_customer`, `invoice_amount`, `invoice_date`, `due_date`, `invoice_currency`, `cust_payment_terms`, `invoice_status`
- optional columns: `payment_date`, `delay_days`, `is_late`, `business_code`, `doc_id`, `document_create_date`, `posting_id`
- checks include unique invoice IDs, positive amounts, ISO dates, due date not before invoice date, payment date not before invoice date, and USD/CAD currency

Files are not uploaded or persisted. The Send to backend action is intentionally disabled until `POST /datasets/upload` exists.

## Backend integration contract

All paths are relative to `VITE_API_BASE_URL`.

| Method | Path | Purpose | Status |
| --- | --- | --- | --- |
| GET | `/dashboard/summary` | Executive aggregates | demo ready |
| GET | `/invoices` | Filtered, sorted, paginated invoices | demo ready |
| GET | `/invoices/{invoice_id}` | Invoice detail, history and context | demo ready |
| GET | `/customers` | Customer directory | demo ready |
| GET | `/customers/{customer_id}` | Customer 360 profile | demo ready |
| GET | `/customers/segments` | Cluster metrics, PCA, stability | demo ready |
| GET | `/payment-risk/summary` | Risk bands, queue and trend | demo ready |
| GET | `/delay-predictions/summary` | Delay distribution and metrics | demo ready |
| GET | `/models/metrics` | Recorded evaluation metrics | demo ready |
| GET | `/insights` | Global feature importance | demo ready |
| GET | `/datasets/quality` | Data quality profile | demo ready |
| GET | `/datasets` | Pipeline artifact inventory | demo ready |
| GET | `/search?q=` | Global invoice and customer search | demo ready |
| GET | `/health` | Mode, version and model status | demo ready |
| POST | `/invoices/predict/late-payment` | Live classifier inference | pending |
| POST | `/invoices/predict/payment-delay` | Live regressor inference | pending |
| POST | `/datasets/upload` | Server-side validation and ingestion | pending |

Prediction request and response shapes are defined in `src/api/index.ts`:

```ts
POST /invoices/predict/late-payment
{ invoice: Record<string, unknown>, customerHistory?: Record<string, unknown> }
=> { probability, riskBand, threshold, modelVersion, predictedAt }

POST /invoices/predict/payment-delay
{ invoice: Record<string, unknown>, customerHistory?: Record<string, unknown> }
=> { predictedDelayDays, interpretation, modelVersion, predictedAt }
```

Response expectations:

- dates as `YYYY-MM-DD`, timestamps as ISO 8601 with timezone
- probabilities as fractions between 0 and 1
- delay values as signed days (negative early, positive late, near zero on time)
- paginated lists return `items`, `page`, `pageSize`, `total`, `totalPages`
- monetary values stay in their original currency with the currency code alongside
- unscored invoices return `null`, never a placeholder score
- report generation pages through `/invoices` and `/customers` with `pageSize=1000`; the backend must keep sorting stable across pages and support that page size

Operational requirements:

- serve the SPA and API on the same origin or configure explicit CORS
- enforce authentication and role checks server-side; the current login is local UI state only
- load artifacts on the server at startup; never expose joblib files or secrets to the browser
- return SHAP values only when actually computed
- expose model versions and health so Data Management and Settings can report availability

## Reports and exports

Reports are assembled client-side from API responses. CSV and PDF downloads stay disabled until a report is generated, and any filter change clears the current report. PDF exports are capped at the first 250 rows; use CSV for the full dataset. Report history is session-only.

## Known missing integrations

- live inference endpoints
- dataset upload and persistence
- real authentication, SSO and server-side authorization
- scheduled or emailed report delivery
- multi-workspace tenancy
- persisted cash-flow run history and approval workflow

These are documented in the UI and are not simulated.
