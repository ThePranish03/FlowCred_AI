# Synthetic financial dataset

> **Simulated data.** Nothing in this directory describes real customers,
> invoices or payments. It is generated by
> `backend/scripts/generate_synthetic_data.py` for experimentation and must never
> be presented as genuine historical business transactions.

The real dataset (`data/processed/flowcred_cleaned.csv`) is read-only and is not
used, modified or replaced by the generator.

## Files

| File | Rows | Contents |
|---|---:|---|
| `synthetic_invoices.csv` | 50,000 | One row per invoice, with settlement state at the observation end |
| `synthetic_payment_transactions.csv` | ~52,600 | Transaction-level ledger, one row per payment instalment |
| `synthetic_customers.csv` | 1,400 | Customer profile, currency, terms, size and activity |
| `generation_metadata.json` | — | Seed, counts, assumptions, censoring statistics, content hashes, validation report |

Derived forecast targets live separately in `data/processed/synthetic/`:

| File | Contents |
|---|---|
| `synthetic_cash_flow_daily.csv` | Daily collections per currency, including genuine zero days |
| `synthetic_cash_flow_weekly.csv` | Monday-start weekly totals, complete weeks only |
| `synthetic_validation.json` | Result of every automated check |

## Key columns

`synthetic_invoices.csv`

- `invoice_id`, `customer_id`, `invoice_date`, `due_date`
- `invoice_amount`, `currency`, `payment_terms`, `payment_terms_days`
- `payment_status` — `paid`, `partially_paid` or `open` **as observed**
- `total_amount_received`, `outstanding_amount`
- `customer_payment_profile` — `early`, `on_time`, `occasional_late`, `chronic_late`, `high_risk`
- `is_censored` / `is_complete` — see below
- `final_payment_date`, `days_to_pay`, `is_late`, `observation_end`
- `source_type` — always `synthetic_simulation`

`synthetic_payment_transactions.csv`

- `transaction_id`, `invoice_id`, `payment_date`, `amount_received`, `currency`
- `transaction_type` — `full_payment`, `partial_payment`, `final_payment`
- `instalment_number`, `instalments_total`

## Right-censoring

The simulation runs past the observation window so the eventual outcome of every
invoice is known. Everything dated after `observation_end` is then **withheld**
from the ledger, and affected invoices are flagged rather than being called
permanently unpaid:

- `is_censored = true` when a payment lands after the window, or the invoice is
  still unsettled but fell due within the last 90 days;
- `is_complete = false` for those rows;
- `payment_status` describes the **observed** state only.

Forecast targets therefore end 90 days before `observation_end`, so only fully
observed weeks are used.

## Reconciliation

For every invoice, `total_amount_received` equals the sum of its ledger rows, and
`outstanding_amount = invoice_amount - total_amount_received`. This is enforced
by validation, not by post-hoc adjustment.

## Regenerate

```bash
backend/.venv/bin/python backend/scripts/generate_synthetic_data.py
backend/.venv/bin/python backend/scripts/generate_synthetic_data.py --seed 7 --invoices 5000
```

Identical configuration and seed reproduce identical files; the content hashes
in `generation_metadata.json` make that checkable.

Validate without writing:

```bash
backend/.venv/bin/python -m pytest backend/tests/test_synthetic_generator.py
```

## Assumptions (configuration, not empirical facts)

- Customer profile mix: 20% early, 35% on time, 25% occasional late, 15% chronic
  late, 5% high risk.
- Payment terms: 15 / 30 / 45 / 60 days with weights 0.28 / 0.44 / 0.20 / 0.08.
- Currency split: 88% USD, 12% CAD; base invoice size differs by currency.
- ~1.2% of business days are posting holidays, and weekend payments shift to the
  next business day — this is what produces genuine zero-collection days.
- Disputes affect ~0.6% of invoices and add a long delay.
